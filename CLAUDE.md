# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A personal laptop AI dev stack, orchestrated via `devops/docker-compose.yml`: PostgreSQL, Ollama, Open WebUI, Milvus (vector store, with etcd + MinIO dependencies), Grafana LGTM observability, OpenObserve (O2) observability, OpenBao (secrets), Passbolt (password manager), and a custom FastAPI backend (`custom-backend/`).

## Structure

- `custom-backend/main.py` — thin FastAPI app: creates the app, mounts the static `/ui` chat page, includes `routers/auth.py` and `routers/chats.py`.
- `custom-backend/db.py` — fetches Postgres (and other) credentials from OpenBao at import time via AppRole, builds the async SQLAlchemy engine, exposes `get_db()`.
- `custom-backend/models.py` — SQLAlchemy ORM models (`UserModel`, `UserChatModel`, `MessageModel`), duplicating `database/init_db.py`'s schema.
- `custom-backend/schemas.py` — all Pydantic request/response schemas.
- `custom-backend/chat_service.py` — LangChain + Milvus setup: `ChatOllama`-backed RAG chain, the `Milvus` vector store client (embeddings via Ollama's `nomic-embed-text`), and the text splitter used for document ingestion.
- `custom-backend/routers/auth.py` — user registration/login/MFA/password endpoints.
- `custom-backend/routers/chats.py` — `/chats`, `/chats/{chat_id}/messages` (GET+POST), and `/chats/{chat_id}/documents` (RAG document ingestion, capped at 5 documents per request), using `chat_service` for the LangChain/Milvus calls.
- `custom-backend/static/index.html` — minimal single-page UI (no build step) for exercising the chat/RAG endpoints by hand, served at `/ui`.
- `custom-backend/entrypoint.sh` — container entrypoint: runs `alembic upgrade head` against `database/alembic/` via `resolve_db_url.py`, which resolves the DB URL from OpenBao and execs Alembic with it in `INIT_DB_DATABASE_URL` (never printed, not exported to uvicorn), then execs uvicorn. Runs on every container start.
- `database/init_db.py` — defines the Alembic-tracked schema (`UserModel`, `UserChatModel`, `MessageModel`, duplicating `custom-backend/models.py`). No longer run directly to create tables; `database/alembic/` migrations (applied by `custom-backend/entrypoint.sh`) are now the source of schema changes. Still reads `INIT_DB_DATABASE_URL` directly, not via OpenBao — `alembic/env.py` uses the same env var.
- `database/alembic/` — Alembic migrations against `init_db.py`'s models. Build context for `custom-backend`'s image is the repo root so this directory can be copied into it.
- `database/init-passbolt-db.sh` / `database/init-openwebui-db.sh` — Postgres init scripts (auto-run on first `postgres-db` start only) that create the separate `passbolt` and `open_webui` databases.
- `devops/docker-compose.yml` — defines all services (including `milvus` and its `milvus-etcd`/`milvus-minio` dependencies, which back Open WebUI's RAG vector store) and the shared `ai-network`. Relative paths in it (build context, bind mounts) are written relative to `devops/` (e.g. `../database/...`), since Compose resolves them against the compose file's directory; build context for `custom-backend` is `..` (repo root), since it copies `database/alembic/` into the image. `devops/.env` is a committed symlink to the root `.env` (un-ignored via `!devops/.env` in `.gitignore`) so Compose's variable interpolation finds it. Pins `name: laptop-ai-backend` so volumes/network keep stable names regardless of invocation directory. Don't pass `--project-directory .` — it would resolve the `../` paths outside the repo.
- OpenObserve (`openobserve` service) — standalone O2 instance running alongside Grafana LGTM, not integrated with it; its web UI/API/OTLP-HTTP ingestion is on port 5080. `open-webui` sends its **logs** here, to stream `openwebui_backend`, via Open WebUI's per-signal OTEL settings (`OTEL_LOGS_OTLP_SPAN_EXPORTER=http`, `OTEL_LOGS_EXPORTER_OTLP_ENDPOINT=http://openobserve:5080/api/default/v1/logs`); its traces and metrics still go to `lgtm` over gRPC. The HTTP exporter uses the endpoint verbatim, so it must be the full `/v1/logs` path. Auth and O2's `stream-name` header both go in `OTEL_EXPORTER_OTLP_LOGS_HEADERS` (`Authorization=Basic%20${OPENOBSERVE_BASIC_AUTH}`, base64 of the root email:password in `.env`) — the OTel exporter ignores that variable whenever Open WebUI passes headers itself, so don't set `OTEL_LOGS_BASIC_AUTH_*` alongside it. O2 rewrites hyphens in stream names to underscores. The root user is created only on O2's first successful start (password needs lower/upper/digit/special), so changing `OPENOBSERVE_ROOT_USER_EMAIL` later doesn't rename it.
- `openbao/` — OpenBao config (`config.hcl`), one-time setup script (`bootstrap.sh`), post-restart unseal script (`auto-unseal.sh`), backup script (`backup.sh`), and the read-only policy for `custom-backend`'s AppRole. See `openbao/README.md`.
- `open-webui-proxy` service + `devops/caddy/Caddyfile` — Caddy HTTPS front for Open WebUI on port 8444 (`tls internal`, local CA in the `caddy-data` volume), for LAN devices: Open WebUI's frontend needs a secure context (`crypto.randomUUID`), which plain `http://<LAN-IP>` isn't. `OPEN_WEBUI_HOST` in `.env` is the LAN IP/hostname it serves.
- `devops/open-webui/functions/signup_email_verification.py` — Open WebUI event Function (not auto-loaded: import it via Admin → Functions and enable it; it lives in Open WebUI's DB, so re-import after editing the file). On `auth.signup` it emails pending users a 2-hour signed link; on `system.startup.completed` it registers the `/api/v1/auths/verify-email` routes on Open WebUI's app (event Functions can't declare routes). The link carries the token in the URL fragment and the page POSTs it, so tokens stay out of access logs and mail scanners can't verify accounts. Verified user ids live in the `fn_email_verified` table in the `open_webui` Postgres DB so an admin can re-suspend a user (set back to `pending`) without them re-verifying. Open WebUI maintainers declined this in core (discussion #31626) and pointed to event Functions. It touches Open WebUI internals (`Users`, `app.router.routes`), so the `open-webui` image is pinned by digest — re-test signup verification when bumping it.
- `devops/open-webui/functions/password_reset.py` — separate event Function (imported/enabled the same way) adding self-service forgot-password (`/api/v1/auths/forgot-password` → emailed link → `/api/v1/auths/reset-password`) and an email notice on `auth.password_changed`. Reset tokens embed a fingerprint of the current password hash, so they're single-use without stored state. Uses more internals than the verification Function (`Auth` table via `get_async_db_context`, `Auths.update_user_password_by_id`, `get_password_hash`, `validate_password`, `revoke_user_tokens`, `publish_event`) — re-test a reset when bumping the image. `revoke_user_tokens` is a no-op without Redis, which this stack doesn't configure.
- `devops/open-webui/functions/password_expiry.py` — separate event Function enforcing 180-day password expiry (added at the user's request despite NIST SP 800-63B advising against periodic changes). Keeps password age in the `fn_password_age` table in the `open_webui` Postgres DB (set on `auth.signup`/`auth.password_changed`, lazily for existing users from Open WebUI's `user.created_at`, clamped so they get at least `grace_days_for_existing` days — Open WebUI has no password-changed timestamp). Since Functions can't veto logins, it replaces the ASGI `.app` of Open WebUI's `POST /api/v1/auths/signin` route with a wrapper that buffers the body, returns 403 for a correct password on an expired account, and otherwise replays the body to the original handler (kept on `__password_expiry_original__` so reloads don't double-wrap). An expired sign-in with the correct password also emails a reset link built in the Password Reset Function's token format (salt `open-webui-password-reset`, sha256 password-hash fingerprint — keep the two Functions in sync), pointing at its `/api/v1/auths/reset-password` page; skipped (popup says ask an admin) when that Function isn't active. Admins are exempt by default (`exempt_admins`). Also serves an admin-only overview at `GET /api/v1/auths/password-expiry` (`?format=json`), guarded by Open WebUI's `get_admin_user` (accepts the browser's `token` cookie); it computes estimated baselines without inserting rows.
- `devops/open-webui/migrations/` — separate Alembic setup for the `fn_*` tables the event Functions keep state in, inside Open WebUI's `open_webui` database. History lives in `fn_alembic_version`, never Open WebUI's own `alembic_version` in the same DB — don't point it at the default version table. Hand-written migrations (no ORM models, `target_metadata = None`), sync engine on psycopg 3 (SQLAlchemy 2.1's default for `postgresql://`). Applied by the one-shot `open-webui-fn-migrate` compose service on every `up` (`open-webui` waits for it), which also mounts the `open-webui-data` volume read-only so the first revision can import rows from the Functions' old SQLite files. The Functions don't create tables themselves — add a new revision here for any schema change. No FKs to Open WebUI's `user` table on purpose (it's owned by Open WebUI's migrations).
- `milvus/` — `init_auth.py`, the one-shot script the `milvus-init-auth` service runs to rotate Milvus's root password.
- `devops/backups/` — gitignored general-purpose backup output directory (separate from `openbao/backups/`, OpenBao's own backup destination).
- `PASSBOLT.md` — one-time admin registration and usage notes for the `passbolt` service.

## Known inconsistencies (don't silently "fix" without asking)

- `custom-backend/models.py` and `database/init_db.py` both declare `UserModel`/`UserChatModel`/`MessageModel` independently (duplicate source of truth) — keep them in sync by hand when changing either.
- Passwords are hashed with `passlib`/`bcrypt` (`pwd_context` in `routers/auth.py`) — not plaintext.
- OpenBao uses file storage with a single unseal key/share (not dev mode, so secrets persist), which means it starts **sealed** after every container restart or host reboot — `custom-backend` will fail to start until `openbao/auto-unseal.sh` is run. This tradeoff was chosen deliberately for a personal laptop stack; don't "fix" it by switching to dev mode without asking, since that would lose secrets on every restart instead.
- `milvus-init-auth` rotates Milvus's root password on every `docker compose up`, not just the first time (Milvus has no env var to set the initial password, and the container doesn't persist whether it already ran) — it fails harmlessly on subsequent runs since `root`/`Milvus` no longer authenticates once rotated. This is a known no-op-after-first-run rather than a bug to "fix" with added state tracking.

## Conventions observed in this repo

- Async SQLAlchemy (`asyncpg` driver) throughout.
- FastAPI with `ORJSONResponse` as the default response class.
- `custom-backend` is split into `db.py`/`models.py`/`schemas.py`/`chat_service.py` plus `routers/` (`auth.py`, `chats.py`) — this split happened once the app grew past a single manageable file (auth + chat + RAG). Keep new endpoints in the router matching their domain rather than growing `main.py` again.

## Configuration

All credentials/secrets/host paths come from environment variables — none are hardcoded in `docker-compose.yml`, `custom-backend/`, or `init_db.py`. `.env` (gitignored, see `.env.example`, both at repo root) holds `OLLAMA_MODELS_PATH` (host path mounted into the `ollama` container), `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `WEBUI_SECRET_KEY`, `INIT_DB_DATABASE_URL` (for running Alembic migrations from the host against the mapped port 5433), `OPENBAO_ROLE_ID`/`OPENBAO_SECRET_ID` (AppRole creds `custom-backend` uses to authenticate to OpenBao — generated by `openbao/bootstrap.sh`, not hand-set), `PASSBOLT_SMTP_USER`/`PASSBOLT_SMTP_PASSWORD`/`PASSBOLT_SMTP_FROM` (Gmail SMTP relay for Passbolt's registration/recovery emails; the user/password are also passed to `open-webui` as `SMTP_USER`/`SMTP_PASSWORD` for signup verification emails), and `MILVUS_ROOT_PASSWORD` (Milvus root user password — rotated in from Milvus's `root`/`Milvus` default by the one-shot `milvus-init-auth` service on first boot, then used by `open-webui` via `MILVUS_TOKEN` to authenticate), and `OPENOBSERVE_ROOT_USER_EMAIL`/`OPENOBSERVE_ROOT_USER_PASSWORD` (OpenObserve root login). `custom-backend`'s LangChain chat endpoints also read `OLLAMA_BASE_URL` (defaults to `http://ollama:11434`) and `DEFAULT_CHAT_MODEL` (defaults to `llama3.2`, must already be pulled into the `ollama` container).

`custom-backend` no longer reads `DATABASE_URL` from the environment — it builds the connection string at startup from Postgres credentials fetched out of OpenBao's `secret/custom-backend` KV path.

## Running things

```bash
docker compose -f devops/docker-compose.yml up -d   # full stack; custom-backend applies migrations on startup via entrypoint.sh
cd openbao && ./bootstrap.sh           # one-time: init/unseal OpenBao, write secrets, create AppRole (see openbao/README.md)
cd openbao && ./auto-unseal.sh         # after any openbao container restart / host reboot
cd custom-backend && uvicorn main:app --reload --port 8001   # backend only, skips migrations (needs OPENBAO_ADDR/OPENBAO_ROLE_ID/OPENBAO_SECRET_ID exported)
export $(grep -v '^#' .env | xargs) && cd database && alembic upgrade head   # apply schema to Postgres from the host (uses INIT_DB_DATABASE_URL against the mapped port 5433)
```
