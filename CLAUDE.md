# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

A personal laptop AI dev stack, orchestrated via `devops/docker-compose.yml`: PostgreSQL, Ollama, Open WebUI, Milvus (vector store, with etcd + MinIO dependencies), Grafana LGTM observability, OpenObserve (O2) observability, OpenBao (secrets), authentik (SSO + TOTP for Open WebUI), Passbolt (password manager, on its own MariaDB), and a custom FastAPI backend (`custom-backend/`).

## Structure

- `custom-backend/main.py` — thin FastAPI app: creates the app, mounts the static `/ui` chat page, includes `routers/auth.py` and `routers/chats.py`.
- `custom-backend/db.py` — fetches Postgres (and other) credentials from OpenBao at import time via AppRole, builds the async SQLAlchemy engine, exposes `get_db()`.
- `custom-backend/models.py` — SQLAlchemy ORM models (`UserModel`, `UserChatModel`, `MessageModel`), duplicating `database/init_db.py`'s schema.
- `custom-backend/schemas.py` — all Pydantic request/response schemas.
- `custom-backend/chat_service.py` — LangChain + Milvus setup: `ChatOllama`-backed RAG chain, the `Milvus` vector store client, and the text splitter used for document ingestion. Embeddings use Ollama's `embeddinggemma` (`EMBEDDING_MODEL`, same model as Open WebUI's `RAG_EMBEDDING_MODEL`) through `PrefixedOllamaEmbeddings`, which adds embeddinggemma's task prefixes (`task: search result | query: ` for queries, `title: none | text: ` for documents; keep in sync with `RAG_EMBEDDING_QUERY_PREFIX`/`RAG_EMBEDDING_CONTENT_PREFIX` on `open-webui`). The Milvus collection is named per model (`custom_backend_docs_<model>`), because vectors from different models aren't comparable even at the same dimension; the old nomic-era `custom_backend_docs` collection is unused. Open WebUI's `rag.embedding_engine`/`rag.embedding_model` are saved DB settings that override the compose env once saved (Admin → Settings → Documents); the prefixes are env-only.
- `custom-backend/routers/auth.py` — user registration/login/MFA/password endpoints.
- `custom-backend/routers/chats.py` — `/chats`, `/chats/{chat_id}/messages` (GET+POST), and `/chats/{chat_id}/documents` (RAG document ingestion, capped at 5 documents per request), using `chat_service` for the LangChain/Milvus calls.
- `custom-backend/static/index.html` — minimal single-page UI (no build step) for exercising the chat/RAG endpoints by hand, served at `/ui`.
- `custom-backend/entrypoint.sh` — container entrypoint: runs `alembic upgrade head` against `database/alembic/` via `resolve_db_url.py`, which resolves the DB URL from OpenBao and execs Alembic with it in `INIT_DB_DATABASE_URL` (never printed, not exported to uvicorn), then execs uvicorn. Runs on every container start.
- `database/init_db.py` — defines the Alembic-tracked schema (`UserModel`, `UserChatModel`, `MessageModel`, duplicating `custom-backend/models.py`). No longer run directly to create tables; `database/alembic/` migrations (applied by `custom-backend/entrypoint.sh`) are now the source of schema changes. Still reads `INIT_DB_DATABASE_URL` directly, not via OpenBao — `alembic/env.py` uses the same env var.
- `database/alembic/` — Alembic migrations against `init_db.py`'s models. Build context for `custom-backend`'s image is the repo root so this directory can be copied into it.
- `database/init-openwebui-db.sh` — Postgres init script (auto-run on first `postgres-db` start only) that creates the separate `open_webui` database.
- `devops/docker-compose.yml` — defines all services (including `milvus` and its `milvus-etcd`/`milvus-minio` dependencies, which back Open WebUI's RAG vector store) and the shared `ai-network`. Relative paths in it (build context, bind mounts) are written relative to `devops/` (e.g. `../database/...`), since Compose resolves them against the compose file's directory; build context for `custom-backend` is `..` (repo root), since it copies `database/alembic/` into the image. `devops/.env` is a committed symlink to the root `.env` (un-ignored via `!devops/.env` in `.gitignore`) so Compose's variable interpolation finds it. Pins `name: laptop-ai-backend` so volumes/network keep stable names regardless of invocation directory. Don't pass `--project-directory .` — it would resolve the `../` paths outside the repo.
- OpenObserve (`openobserve` service) — standalone O2 instance running alongside Grafana LGTM, not integrated with it; its web UI/API/OTLP-HTTP ingestion is on port 5080. `open-webui` sends its **logs** here, to stream `openwebui_backend`, via Open WebUI's per-signal OTEL settings (`OTEL_LOGS_OTLP_SPAN_EXPORTER=http`, `OTEL_LOGS_EXPORTER_OTLP_ENDPOINT=http://openobserve:5080/api/default/v1/logs`); traces and metrics are off (`ENABLE_OTEL_TRACES/METRICS=false`) since `lgtm` became opt-in (compose profile `lgtm`, not started by default, to save ~0.8 GB RAM on the 16 GB soldered-RAM laptop; `--profile lgtm up -d lgtm` brings it back with its `lgtm-data` history, then turn those two flags back on). Don't re-add `lgtm` to `open-webui`'s `depends_on` — a profiled service there breaks a default `up`. The HTTP exporter uses the endpoint verbatim, so it must be the full `/v1/logs` path. Auth and O2's `stream-name` header both go in `OTEL_EXPORTER_OTLP_LOGS_HEADERS` (`Authorization=Basic%20${OPENOBSERVE_BASIC_AUTH}`, base64 of the root email:password in `.env`) — the OTel exporter ignores that variable whenever Open WebUI passes headers itself, so don't set `OTEL_LOGS_BASIC_AUTH_*` alongside it. O2 rewrites hyphens in stream names to underscores. The root user is created only on O2's first successful start (password needs lower/upper/digit/special), so changing `OPENOBSERVE_ROOT_USER_EMAIL` later doesn't rename it.
- `openwebui-audit-shipper` service + `devops/otel-collector/openwebui-audit.yaml` — OpenTelemetry Collector (contrib, pinned) that tails Open WebUI's audit log (`AUDIT_LOG_LEVEL=METADATA` on `open-webui`, written to `audit.log` in the `open-webui-data` volume, mounted read-only here) into O2 stream `openwebui_audit`, so O2 shows which user did what — Open WebUI's regular OTel logs carry no user, and its audit entries go only to that file (loguru sink), never through the OTel log handler. Read offsets persist in the `otelcol-audit-storage` volume (runs as root only so it can write there). Keep the level at `METADATA`: `REQUEST` would log sign-in passwords. Open WebUI itself runs at `GLOBAL_LOG_LEVEL=WARNING` (stdout and the OTel logs to `openwebui_backend` both stop at WARNING; INFO was ~97% of that stream); the audit file has its own INFO-level sink, unaffected. A second pipeline (`logs/queries`, own exporter for the `stream-name` header) tails `query.log` from the same volume into stream `openwebui_queries` (see `query_log.py`). The config file is a single-file bind mount and compose doesn't notice its content changing: apply edits with `up -d --no-deps --force-recreate openwebui-audit-shipper`.
- `ollama-log-shipper` service + `devops/otel-collector/ollama-logs.yaml` — tails Ollama's Docker json-file log into O2 stream `ollama`, keeping only `[GIN]` request lines (columns `status`, `duration`, `duration_ms`, `client_ip`, `method`, `path`; 5xx → ERROR, 4xx → WARN) and logfmt server events (`level`, `msg`, `source`), and dropping llama.cpp runner output (~80% of the log). Body is time first (UTC, no suffix), like `openwebui_audit`. It reads the file (only `/var/lib/docker/containers/${OLLAMA_CONTAINER_ID}`, read-only) instead of using a logging driver because `ollama` must never be stopped or recreated without the user choosing to; after the user recreates it, set `OLLAMA_CONTAINER_ID` in `.env` to the new `docker inspect -f '{{.Id}}' laptop-ollama` and recreate the shipper (`up -d --no-deps ollama-log-shipper`). Ollama logs a 500 whenever the caller hangs up (Stop/Regenerate in the UI, or an `open-webui` restart mid-reply) — check `open-webui`'s log for a real error before treating it as an Ollama failure. Offsets persist in `otelcol-ollama-storage`.
- `openbao-audit-shipper` service + `devops/otel-collector/openbao-audit.yaml` — same collector setup tailing OpenBao's audit log into O2 stream `openbao_audit` (who read/changed which secret path, from where, and the error, e.g. `permission denied`). The audit device is declared in `openbao/config.hcl` (`audit "file" "file"` → `/openbao/logs/audit.log` in the `openbao-logs` volume), since OpenBao doesn't allow enabling audit devices through the API by default. Secret values, tokens and accessors are HMAC-hashed by OpenBao. Only `response` entries are shipped (each repeats its request and adds the outcome); `user` is the userpass username, AppRole role name or token display name. While the device is enabled OpenBao rejects requests it can't log, so the volume must stay writable. The file isn't rotated. Offsets persist in `otelcol-openbao-audit-storage`.
- `searxng` service + `devops/searxng/settings.yml` — SearXNG (pinned tag) as Open WebUI's web search engine (`ENABLE_WEB_SEARCH`, `WEB_SEARCH_ENGINE=searxng`, `SEARXNG_QUERY_URL=http://searxng:8080/search`). Internal only (no published port), so the bot limiter is off (it would also need Valkey). `search.formats` must include `json` or Open WebUI's `?format=json` requests get 403. `web.search.enable`/`engine`/`searxng_query_url` are persisted Open WebUI config that override env once saved (the DB had `enable=false` saved; it was deleted so env applies). Regular users have the chat Controls panel hidden (`chat.controls`/`valves`/`system_prompt`/`params` = false in the saved `user.permissions` row, set by hand there and mirrored in compose's `USER_PERMISSIONS_CHAT_*` for fresh installs), and Edit, Read Aloud and Fork under answers (`chat.edit`/`tts`/`import` = false, set the same way; in 0.11.3 `chat.edit` gates only an answer's Edit, not editing one's own question, and Fork has no permission of its own — it's shown only with `chat.import`, so importing chats goes too). Info under answers has no permission; `loader.js` hides it. Open WebUI only hides these in the UI and doesn't enforce them server-side. Web search is on by default for all users via `DEFAULT_INTERFACE_SETTINGS={"webSearch": "always"}` (the per-user Settings → Interface → Web Search "Always" value; a user's own setting still wins, merged in `routers/users.py`). It's persisted as `ui.default_interface_settings`, which was saved as `{}` and deleted so env applies. (`DEFAULT_MODEL_METADATA`'s `defaultFeatureIds` would only pre-tick the toggle per chat.) `SEARXNG_SECRET` in `.env`. Engines are SearXNG's defaults plus `google` and `bing` (enabled in settings.yml): the defaults have only three web engines (brave, duckduckgo, google cse), and on 2026-10-03 a burst of eval and test searches got all three blocked at once (too many requests / CAPTCHA), after which `process_web_search` raised "No results found from web search" and Open WebUI answered without sources. settings.yml is a single-file bind mount, so apply edits with `up -d --no-deps --force-recreate searxng`. Space out bulk searches (evals) to avoid this. Reranking (hybrid search, for web results and documents) uses a local SentenceTransformers cross-encoder inside `open-webui`, `RAG_RERANKING_MODEL` in `.env` (default `cross-encoder/ms-marco-MiniLM-L6-v2`, ~90 MB, ~0.5 s per 12 chunks on CPU); env applies only while no `rag.reranking_model` row is saved, and the model loads at startup or on Admin → Settings → Documents → Save (writing the DB row alone doesn't reload it). It was once the `external` engine pointed at `http://ollama:11434`, which has no rerank API: every search logged `405` and fell back to the untrimmed candidates, so don't raise `rag.top_k` while the reranker is broken. `rag.top_k`=6/`rag.top_k_reranker`=3 (saved DB values): Open WebUI keeps `top_k_reranker` chunks per generated query and then merges all 2–4 queries capped at `top_k`, so `top_k` is also how many web chunks the 3B model reads (plus, until 2026-10-03, up to 3 from the Family knowledge collection then attached to `fast-ai`); 12 made answers take ~2 min on CPU (reading ~50–70 s, embedding pages ~0.3 s per chunk; embedding batch size makes no difference). Saved DB-only setting: `web.search.domain.filter_list` blocks sites that never yield text to the plain-HTTP loader (`!investing.com` 403, `!youtube.com` title only, `!timeanddate.com` Cloudflare, `!facebook.com` login, `!bseindia.com` redirect, `!mybharat.gov.in`/`!findoc.com` JS-only, `!linkedin.com` comment noise); the filter runs before the result-count cut, so blocked results are replaced. Wikipedia returns its robot-policy page because `USER_AGENT` is unset. Speed (2026-10-03): embedding the fetched pages (embeddinggemma via Ollama, ~0.28 s per chunk, 90–370 chunks per question) is the slowest step (18–100 s), then the answer (35–70 s for a 1,400–2,800-token prompt). `web.search.result_count`=8 is a saved DB value (compose says 3); don't lower it for speed: re-running recent searches showed 8 of 23 sources answers used ranked 5th–8th. Keep `task.query.retrieval.enable` on: chunk selection over web results reuses the generated search queries (`request.state.cached_queries`), and with it off falls back to the raw question. `task.tags.enable` is off (tags only label chats in the sidebar; saves a model call that held up the next question).
- `authentik-events-shipper` service + `devops/otel-collector/authentik-events.yaml` — authentik audit events → O2 stream `authentik_events`. `authentik-server`/`-worker` use the `fluentd` logging driver (`fluentd-address: 127.0.0.1:24224`, `fluentd-async: "true"` so authentik never blocks on the shipper) into the collector's `fluentforward` receiver; the port is published on 127.0.0.1 because the Docker daemon, not a container, connects to it. The filter keeps only lines containing `"event": "Created Event"` (that OTTL condition must stay YAML-quoted, since its `": "` otherwise parses as a map), and transform parses the JSON, sets the time from authentik's naive-UTC `timestamp`, and stringifies `context` so O2 doesn't flatten the whole HTTP request into columns.
- `openbao/` — OpenBao config (`config.hcl`), one-time setup script (`bootstrap.sh`), post-restart unseal script (`auto-unseal.sh`), backup script (`backup.sh`), the read-only policy for `custom-backend`'s AppRole, and `setup-users.sh`, which creates the human userpass logins `bao-admin` (policy `user-admin`, `policy-user-admin.hcl`) and `bao-readonly` (policy `user-readonly`, read/list all of `apps/`) from `OPENBAO_ADMIN_PASSWORD`/`OPENBAO_READONLY_PASSWORD` in `.env` — the root token in `keys.json` is break-glass only. When `OPENBAO_OIDC_CLIENT_ID`/`OPENBAO_OIDC_CLIENT_SECRET` are set, `setup-users.sh` also enables the `oidc` auth method (sign-in through authentik, password + TOTP; see `authentik/blueprints/openbao-sso.yaml`): discovery at `https://${OPEN_WEBUI_HOST}:9443/application/o/openbao/` with Caddy's public root cert as `oidc_discovery_ca_pem` (read from `open-webui-proxy`), two roles whose `token_policies` set the access — `readonly` (default role, policy `user-readonly`, `bound_claims` groups `openbao-admins`/`openbao-readers`) and `admin` (`user-admin`, `openbao-admins` only) — so admins sign in read-only unless they enter role `admin`; `preferred_username` → metadata `username`. No identity groups on purpose: an external group with a policy would grant it on every login regardless of role (the script deletes the earlier `authentik` role and `openbao-admins`/`openbao-readers` identity groups). The userpass logins stay as the fallback for when authentik is down; both methods are listed on the UI login page. See `openbao/README.md`. `bootstrap.sh` writes every app's secrets under one KV layout, `apps/<environment>/<app>` (KV v2 engine mounted at `apps/`; it was `secret/`, then briefly `secrets/`, and re-running `bootstrap.sh` moves an old mount with `bao secrets move` and deletes old-layout paths) with this stack as `default`: `apps/default/custom-backend` (the only one an app reads, via AppRoles whose policies allow just that path) plus copies of the other services' `.env` secrets in `apps/default/{postgres,open-webui,milvus,authentik,passbolt,openobserve,searxng}` (`apps/default/authentik` also holds `mfa_required`, a copy of the `AUTHENTIK_MFA_REQUIRED` setting, and `apps/default/open-webui` holds `reranking_model`, a copy of `RAG_RERANKING_MODEL`); nothing consumes those copies yet (services still read `.env`), so re-run `bootstrap.sh` after rotating a value in `.env`. It refuses to write an empty value (a misspelled `.env` key stops it), and deletes the pre-layout flat paths (`apps/custom-backend`, `apps/authentik`, …). `custom-backend` reads `OPENBAO_SECRET_MOUNT` (default `apps`) and `OPENBAO_SECRET_PATH` (default `default/custom-backend`).
- `open-webui-proxy` service + `devops/caddy/Caddyfile` — Caddy HTTPS front for Open WebUI on port 8444 (`tls internal`, local CA in the `caddy-data` volume), for LAN devices: Open WebUI's frontend needs a secure context (`crypto.randomUUID`), which plain `http://<LAN-IP>` isn't. `OPEN_WEBUI_HOST` in `.env` is the LAN IP/hostname it serves. On authentik's `:9443` site it redirects only the bare path `/` (authentik's root-redirect, where flows without a `next` end, which would show the app library) to `https://{host}:8444/`; everything else proxies to `authentik-server:9000`. The Caddyfile is a single-file bind mount, so after editing it recreate `open-webui-proxy` (`caddy reload` would still read the old inode).
- `devops/open-webui/functions/signup_email_verification.py` — Open WebUI event Function (not auto-loaded: import it via Admin → Functions and enable it; it lives in Open WebUI's DB, so re-import after editing the file). On `auth.signup` it emails pending users a 2-hour signed link; on `user.created` with source `oauth` (SSO account creation never emits `auth.signup`) it instead promotes the pending user to `user` and records them in `fn_email_verified` (Valve `activate_sso_users`, default on — authentik's self-enrollment and invitation flows both confirm the email before the account is active; off → SSO users get the email too). Event Functions are dispatched in a background task, so that promotion races the post-login redirect (one DB update vs. a page load; a reload fixes a lost race); on `system.startup.completed` it registers the `/api/v1/auths/verify-email` routes on Open WebUI's app (event Functions can't declare routes). The link carries the token in the URL fragment and the page POSTs it, so tokens stay out of access logs and mail scanners can't verify accounts. Verified user ids live in the `fn_email_verified` table in the `open_webui` Postgres DB so an admin can re-suspend a user (set back to `pending`) without them re-verifying. Open WebUI maintainers declined this in core (discussion #31626) and pointed to event Functions. It touches Open WebUI internals (`Users`, `app.router.routes`), so the `open-webui` image is pinned by digest — re-test signup verification when bumping it.
- `devops/open-webui/functions/password_reset.py` — separate event Function (imported/enabled the same way) adding self-service forgot-password (`/api/v1/auths/forgot-password` → emailed link → `/api/v1/auths/reset-password`) and an email notice on `auth.password_changed`. Reset tokens embed a fingerprint of the current password hash, so they're single-use without stored state. Uses more internals than the verification Function (`Auth` table via `get_async_db_context`, `Auths.update_user_password_by_id`, `get_password_hash`, `validate_password`, `revoke_user_tokens`, `publish_event`) — re-test a reset when bumping the image. `revoke_user_tokens` is a no-op without Redis, which this stack doesn't configure.
- `devops/open-webui/functions/password_expiry.py` — separate event Function enforcing 180-day password expiry (added at the user's request despite NIST SP 800-63B advising against periodic changes). Keeps password age in the `fn_password_age` table in the `open_webui` Postgres DB (set on `auth.signup`/`auth.password_changed`, lazily for existing users from Open WebUI's `user.created_at`, clamped so they get at least `grace_days_for_existing` days — Open WebUI has no password-changed timestamp). Since Functions can't veto logins, it replaces the ASGI `.app` of Open WebUI's `POST /api/v1/auths/signin` route with a wrapper that buffers the body, returns 403 for a correct password on an expired account, and otherwise replays the body to the original handler (kept on `__password_expiry_original__` so reloads don't double-wrap). An expired sign-in with the correct password also emails a reset link built in the Password Reset Function's token format (salt `open-webui-password-reset`, sha256 password-hash fingerprint — keep the two Functions in sync), pointing at its `/api/v1/auths/reset-password` page; skipped (popup says ask an admin) when that Function isn't active. Admins are exempt by default (`exempt_admins`). Also serves an admin-only overview at `GET /api/v1/auths/password-expiry` (`?format=json`), guarded by Open WebUI's `get_admin_user` (accepts the browser's `token` cookie); it computes estimated baselines without inserting rows.
- `devops/open-webui/functions/authentik_user_cleanup.py` — separate event Function (imported/enabled the same way): deleting a user in Open WebUI (Admin → Users → Delete) archives their chats into `fn_archived_chats` first (Valve `archive_chats`, default on; an archive failure returns 500 without deleting, and a failed delete removes the copies again), also deletes their authentik user, and then purges what Open WebUI leaves behind (memories + `user-memory-<id>` vectors, notes, tags, chat_file rows, uploaded files incl. knowledge links, the file on disk and `file-<id>` vectors via `ASYNC_VECTOR_DB_CLIENT.delete_collection` — Open WebUI's own file delete calls `delete()` without ids, which leaves the Milvus collection — and `fn_email_verified`/`fn_password_age`; `fn_user_sso_status` is kept, its sync script marks people `removed`). Admin-only archive pages at `/api/v1/archived-chats` (list, transcript, `?format=json`, DELETE), registered like Password Expiry's overview and guarded by `get_admin_user`. Users are family/friends on a personal stack, so archiving by default is a courtesy, not a compliance question; turn the Valve off for someone who asked to be erased. `user.deleted` fires after the row is gone with only the id, so it wraps the ASGI `.app` of `DELETE /api/v1/users/{user_id}` instead (same technique as Password Expiry; original kept on `__authentik_cleanup_original__`), reads `user.oauth.oidc.sub` and email first, and after a 200 deletes the authentik user in a background task. Matches by `uid` == `sub` (the provider's `sub_mode: hashed_user_id`; the users API can't filter by uid, so it pages through all users), else by a single exact email match; never deletes superusers or service accounts. Calls `http://authentik-server:9000` (`AUTHENTIK_API_URL`) with `AUTHENTIK_API_TOKEN` (= `OPEN_WEBUI_AUTHENTIK_API_TOKEN` in `.env`), the token of the `open-webui-user-sync` service account from `authentik/blueprints/open-webui-user-sync.yaml` (role with only `view_user`/`delete_user`).
- `devops/open-webui/functions/audit_status_code.py` — separate event Function (imported/enabled the same way, then restart `open-webui`) that makes Open WebUI's audit log record the HTTP response status at `AUDIT_LOG_LEVEL=METADATA`: Open WebUI only captures it at `REQUEST_RESPONSE` (which also logs bodies), so without this every entry has `"response_status_code": null`. Patches `open_webui.utils.audit.AuditLoggingMiddleware` at class level (`__call__` wraps `send` to note the `http.response.start` status in the ASGI scope; `_log_audit_entry` fills it in only when Open WebUI left it empty), originals kept on `__audit_status_original_call__`/`_log__` so reloads don't double-wrap. Disabling doesn't unpatch the running process — restart after. Uses internals: re-test (an audited request shows a status in `audit.log`) when bumping the image. Requests ending in an unhandled exception keep `null`, which `openwebui-audit.yaml` shows as `-`.
- `devops/open-webui/functions/chat_soft_delete.py` — separate event Function (imported/enabled the same way, then restart `open-webui`): Open WebUI hard-deletes chats (rows removed, no trash), so this patches `open_webui.models.chats.ChatTable` at class level (`delete_chat_by_id`, `delete_chat_by_id_and_user_id`, `delete_chats_by_user_id`, `delete_chats_by_user_id_and_folder_id` — one chat incl. internal child chats, "delete all chats", folder deleted with contents) to upsert the affected chat rows + `chat_message` rows into `fn_archived_chats` (reason `chat_deleted`) before calling the original; a failed copy is logged and the delete still happens. It skips copying while `UsersTable.delete_user_by_id` runs (context variable), so whole-user deletion stays governed by the User Cleanup Function's `archive_chats` Valve (reason `account_deleted`). Admin-only `POST /api/v1/archived-chats/{chat_id}/restore` re-inserts a `chat_deleted` chat for its still-existing owner (no folder, unpinned, unshared; `chat_message` via `json_populate_recordset`) and removes the archive row; the User Cleanup Function's archive pages show the reason and a Restore button. Single-message deletes aren't covered. Originals on `__soft_delete_original__`. Uses internals — re-test delete → archive → restore when bumping the image. Tested end to end with a throwaway chat.
- `devops/open-webui/functions/chat_history_trim.py` — filter Function (imported/enabled, **not** global; attached to `fast-ai:latest` via the model's `meta.filterIds`). Uses Open WebUI's `request` filter hook, which runs at the end of `process_chat_payload` — after web search and after the search results are put into the latest user message — so query generation still sees the recent chat (follow-ups like "where is he from?" resolve) while the model answering gets only system messages + the latest user message (Valve `keep_previous_turns`, default 0). Fixes the 3B model answering the previous question in multi-topic chats. Trade-off: "summarize your last answer"-style questions have no history with this model. No restart needed (model list refreshes on the next `/api/models`).

## Known inconsistencies (don't silently "fix" without asking)

- `custom-backend/models.py` and `database/init_db.py` both declare `UserModel`/`UserChatModel`/`MessageModel` independently (duplicate source of truth) — keep them in sync by hand when changing either.
- Passwords are hashed with `passlib`/`bcrypt` (`pwd_context` in `routers/auth.py`) — not plaintext.
- OpenBao uses file storage with a single unseal key/share (not dev mode, so secrets persist), which means it starts **sealed** after every container restart or host reboot — `custom-backend` will fail to start until `openbao/auto-unseal.sh` is run. This tradeoff was chosen deliberately for a personal laptop stack; don't "fix" it by switching to dev mode without asking, since that would lose secrets on every restart instead.
- `milvus-init-auth` rotates Milvus's root password on every `docker compose up`, not just the first time (Milvus has no env var to set the initial password, and the container doesn't persist whether it already ran) — it fails harmlessly on subsequent runs since `root`/`Milvus` no longer authenticates once rotated. This is a known no-op-after-first-run rather than a bug to "fix" with added state tracking.

## Conventions observed in this repo

- Async SQLAlchemy (`asyncpg` driver) throughout.
- FastAPI with `ORJSONResponse` as the default response class.
- `custom-backend` is split into `db.py`/`models.py`/`schemas.py`/`chat_service.py` plus `routers/` (`auth.py`, `chats.py`) — this split happened once the app grew past a single manageable file (auth + chat + RAG). Keep new endpoints in the router matching their domain rather than growing `main.py` again.

update after ollama is recreated), `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `WEBUI_SECRET_KEY`, `INIT_DB_DATABASE_URL` (for running Alembic migrations from the host against the mapped port 5433), `OPENBAO_ROLE_ID`/`OPENBAO_SECRET_ID` (AppRole creds `custom-backend` uses to authenticate to OpenBao — generated by `openbao/bootstrap.sh`, not hand-set), `OPENBAO_ADMIN_PASSWORD`/`OPENBAO_READONLY_PASSWORD` (passwords for the human OpenBao logins `openbao/setup-users.sh` creates), `PASSBOLT_SMTP_USER`/`PASSBOLT_SMTP_PASSWORD`/`PASSBOLT_SMTP_FROM` (Gmail SMTP relay for Passbolt's registration/recovery emails; the user/password are also passed to `open-webui` as `SMTP_USER`/`SMTP_PASSWORD` for signup verification emails), `PASSBOLT_DB_PASSWORD` (MariaDB password for the `passbolt` user on `passbolt-db`), and `MILVUS_ROOT_PASSWORD` (Milvus root user password — rotated in from Milvus's `root`/`Milvus` default by the one-shot `milvus-init-auth` service on first boot, then used by `open-webui` via `MILVUS_TOKEN` to authenticate), and `OPENOBSERVE_ROOT_USER_EMAIL`/`OPENOBSERVE_ROOT_USER_PASSWORD` (OpenObserve root login), `AUTHENTIK_SECRET_KEY`/`AUTHENTIK_BOOTSTRAP_EMAIL`/`AUTHENTIK_BOOTSTRAP_PASSWORD` (authentik; bootstrap values only apply on its first start), and `OPEN_WEBUI_OIDC_CLIENT_ID`/`OPEN_WEBUI_OIDC_CLIENT_SECRET` (Open WebUI's OIDC client, written into authentik by the blueprint), and `OPENBAO_OIDC_CLIENT_ID`/`OPENBAO_OIDC_CLIENT_SECRET` (OpenBao's OIDC client, written into authentik by `openbao-sso.yaml` and into OpenBao by `setup-users.sh`), and `RAG_RERANKING_MODEL` (Open WebUI's reranker, a setting not a secret; see the `searxng` bullet). `custom-backend`'s LangChain chat endpoints also read `OLLAMA_BASE_URL` (defaults to `http://ollama:11434`) `DEFAULT_CHAT_MODEL` (defaults to `llama3.2`, must already be pulled into the `ollama` container), and `CHAT_TEMPERATURE` (defaults to `0.1`, matching Open WebUI's `DEFAULT_MODEL_PARAMS` in `docker-compose.yml`, whose saved `models.default_params` DB row overrides the env once it exists).

`custom-backend` no longer reads `DATABASE_URL` from the environment — it builds the connection string at startup from Postgres credentials fetched out of OpenBao's `apps/default/custom-backend` KV path (`OPENBAO_SECRET_PATH`).

## Running things

```bash
docker compose -f devops/docker-compose.yml up -d   # full stack; custom-backend applies migrations on startup via entrypoint.sh
cd openbao && ./bootstrap.sh           # one-time: init/unseal OpenBao, write secrets, create AppRole (see openbao/README.md)
cd openbao && ./auto-unseal.sh         # after any openbao container restart / host reboot
cd custom-backend && uvicorn main:app --reload --port 8001   # backend only, skips migrations (needs OPENBAO_ADDR/OPENBAO_ROLE_ID/OPENBAO_SECRET_ID exported)
export $(grep -v '^#' .env | xargs) && cd database && alembic upgrade head   # apply schema to Postgres from the host (uses INIT_DB_DATABASE_URL against the mapped port 5433)
```
